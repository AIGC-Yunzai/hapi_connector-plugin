# 出站引用的两个偏离：频道用消息 id，自己发的消息靠发送索引

ADR-0001 写的是「引用回复用 `REFIDX_`，不能用 `message.id`」。那条结论对群聊与私聊成立，
但覆盖不了两种场景，这里补记。

## 场景一：频道

频道（`/channels/{channel_id}/messages`）与频道私信走的是 guild 接口，引用参数就是被引消息的
`id` 本身。官方 Python SDK 的「发送引用消息」示例就是 `Reference(message_id=message.id)` 配
`post_message(channel_id=…)`，全程没有 `REFIDX` 这个词。

因此按 scope 分流：频道把显式 id 原样写进 `message_reference`，其余场景才走 REFIDX 那一套。

AstrBot 在这件事上是**缺口而不是基准**：它出站统一按「`REFIDX_` 优先、否则取本条事件的
`msg_idx`」处理，而频道事件的 `raw_data` 里没有 `message_scene`，取到的永远是空串——等于它在
频道场景下发不出任何引用。照抄它会把这个问题一起抄过来。

## 场景二：引用机器人自己发过的消息

平台要求 `message_reference.message_id` 是 `REFIDX_` 形态，但发送结果只回一个 `ROBOT1.0_` 形态的
`id`，`REFIDX` 藏在响应的 `ext_info.ref_idx` 里。插件之间传递的通常只有 `message_id`，于是「回
上一条我发的」这条路走不通，还会静默退化成「引用用户当前这条」。

决定：发送成功时把 `id → ext_info.ref_idx` 记进一张进程内索引，出站引用解析时按
「显式 REFIDX → 索引 → 本条被动消息」的顺序查。

## 为什么索引不落盘

- 它不是需要备份的状态，丢了只影响历史消息的回引，不影响任何当期行为；
- `REFIDX` 的语义由平台定义，跨会话、跨重连是否继续有效并无文档保证，持久化等于把未验证的
  假设写进磁盘；
- 一张有上限的表（500 条，淘汰最早记入的）已经覆盖「刚发完就想回引」这个真实场景，再多的历史
  引用应该走「重新发一条」。

索引只活在进程内，因此重启后引用旧消息会退化为「引用本条」或「不引用」——这条退化路径是有意的，
不是遗漏。
