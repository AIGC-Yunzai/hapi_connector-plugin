# 锅巴管理官方 QQ 机器人，并给 hapi 通道一套独立的消息策略

## Problem Statement

官方 QQ 机器人已经能收发消息了，但仍然是「配置靠手改 yaml、状态靠猜」的状态：

- 锅巴里看不到有哪些官方机器人，也没法删。停用一个 bot 要手动改 `config/config/qqbot.yaml` 再重启云崽。
- hapi 的文本推送发给官方 bot 时**一条都发不出去，而且不报错**：推送走合并转发段，适配器不认这个段类型，拆出来是空数组，直接被丢掉。
- 模型回复末尾会带一段 `AGENT_NOTIFY_SUMMARY {"status":…}` 的机器文本，hapi 自己的 WebUI 会把它剥掉，我们的适配器没剥，用户看到的是裸 JSON。
- 推送级别和输出方式只有全局一份。官方 bot 支持原生 markdown、不适合发图片，但改了全局设置会连带影响 OneBot 群。

## Solution

锅巴里新增一个「官方机器人」标签页，用来查看、删除、改备注、停用官方机器人，并给出扫码新增的文字指引。

给官方机器人一套**只对它生效**的通道策略：推送级别、输出方式、摘要回复是否固定走原生 markdown。OneBot 的现有行为完全不变。

同时修好推送链路本身：合并转发段降级为文本，`AGENT_NOTIFY_SUMMARY` 页脚从正文剥离。

## User Stories

1. 作为云崽主人，我想在锅巴里看到所有已添加的官方机器人，以便知道当前有哪些账号在跑。
2. 作为云崽主人，我想在锅巴里看到每个官方机器人的备注和在线状态，以便判断它有没有连上。
3. 作为云崽主人，我想在锅巴里删除一个官方机器人，以便停用一个不再使用的 bot 而不用去改 yaml。
4. 作为云崽主人，我想删除后凭证从本地立刻抹掉、连接立刻断开，以便不用担心残留。
5. 作为云崽主人，我想在锅巴里改备注，以便区分多个 bot 各自的用途。
6. 作为云崽主人，我想在锅巴里临时停用某个 bot，以便保留凭证但停止收发。
7. 作为云崽主人，我想停用后立即掉线、重新启用后立即连上，以便不用重启云崽。
8. 作为云崽主人，我想在锅巴里看到「用 `#hapi qqbot login` 扫码添加」的提示，以便知道新增入口在哪。
9. 作为云崽主人，我想在锅巴里看不到 AppSecret，以便减少泄露和误改的机会。
10. 作为云崽主人，我想让官方机器人的推送级别独立于 OneBot，以便给 bot 设成 summary 而群里仍保持 detail。
11. 作为云崽主人，我想让官方机器人的输出方式独立，以便在 bot 上用原生 markdown 而不是渲染图片。
12. 作为云崽主人，我想让摘要回复始终以原生 markdown 文本发送，以便在手机上直接读到结论和表格。
13. 作为云崽主人，我想在「仅图片」模式下摘要不出现在图片里，以便不重复占用流量。
14. 作为云崽主人，我想让这套策略也作用于 `#hapi msg` 手动查看，以便手动看和自动推的格式一致。
15. 作为云崽主人，我想在官方 bot 上继续用 `>` 前缀发消息，以便不改变已有的肌肉记忆。
16. 作为云崽主人，我想用原生 `#设置主人` 把某个 QQ 号设为这个 bot 的主人，以便它能执行 `#hapi` 指令和快捷发送。
17. 作为云崽主人，我想在登录成功后看到「请私聊该机器人发送 `#设置主人`」的提示，以便知道下一步该做什么。
18. 作为云崽主人，我想让官方 bot 收到合并转发时自动降级成文本，以便消息不会静默消失。
19. 作为云崽主人，我想让回复正文里不再出现 `AGENT_NOTIFY_SUMMARY` 这段机器文本，以便阅读干净。
20. 作为 OneBot 用户，我想我现有的推送格式、推送级别和行为完全不变，以便升级不产生回归。

## Implementation Decisions

**配置项（三个，全局一份）**

官方机器人通道的策略由三个键控制，都写进默认配置文件——否则配置加载时会把未知键当成脏数据删掉。

- 推送级别：`inherit` | `detail` | `simple` | `collapsed` | `summary` | `silence`，默认 `inherit`（跟随全局）。
- 输出方式：`text` | `image` | `both`，默认 `text`。
- 摘要固定走 markdown：布尔，默认开。

**通道策略的判定**

策略按「会话当前归属的那个聊天窗口」判定，而不是按会话本身。一个会话同一时刻只有一个归属窗口，因此推送内容在产出时就能确定该用哪套参数，不需要在发送时二次转换。判定依据是窗口的 bot 对象所挂适配器标识，不是窗口键里的前缀。

**摘要消息的判定**

优先级从高到低：

1. 本批 `assistant-reply` 中带有合法 `AGENT_NOTIFY_SUMMARY` 页脚的那一条；
2. 否则取本批最后一条 `assistant-reply`；
3. 都没有则为空。

页脚剥离无条件生效（与是否「摘要固定走 markdown」无关）。匹配规则必须移植 hapi 自己的实现，而不是写一条贪婪正则：页脚允许粘在正文同一行（`Done.AGENT_NOTIFY_SUMMARY {…}`），也允许缩进，但要拒绝普通叙述里的提及（`Example: AGENT_NOTIFY_SUMMARY …`）。

**发送矩阵**（摘要固定走 markdown 开启时）

记 `M` 为按推送级别过滤后的消息集合，`S` 为摘要消息，`R = M \ S`：

- `text`：一条原生 markdown，含 `M` 全部，不拆分。
- `image`：一条原生 markdown（`header + S`），加一张 markdown 图片（`header + R`）；`R` 为空则不发图。
- `both`：一条原生 markdown（`header + M`），加一张 markdown 图片（`header + R`）；`R` 为空则不发图。

关闭「摘要固定走 markdown」时退化为现有语义（三种模式都不拆分）。

**合并转发降级**

分两层：

1. 适配器的消息段拆分增加对合并转发段的处理，把各节点的正文按顺序拍平成文本，节点之间空行分隔。这是兜底，任何插件往官方机器人发合并转发都不该静默消失。
2. hapi 侧在目标窗口是官方机器人时，不构造合并转发段，直接产出文本/markdown，避免「先包成转发再拍平」。

**锅巴标签页**

新增第三组标签页（分页标签至少两组才生效，现有两组，加完是三组）。组内两组内容：

- 机器人列表：多卡片表单，每张卡有备注、AppID（只读）、状态（只读）、启用开关。卡片的删除由表单自带二次确认。
- 通道设置：上面三个配置项。

AppSecret 不出现在表单里，既不展示也不提交。

**账号表的读写语义**

账号表仍然是独立文件，不并入主配置。锅巴通过两个回调桥接：

- 读取时把账号表映射成卡片数组，追加进返回的配置对象。
- 保存时对提交的数组与当前账号表求差集：只在旧表里的删除并断连；两边都有的更新备注与启用状态；只在提交里出现的忽略（新增只能走扫码或命令行）。

这两个展示用字段必须在写盘前剔除，不能落进主配置文件。启用状态变化立即生效：关则断开，开则连接。

**主人绑定**

不新建白名单。复用 Yunzai 原生的 `#设置主人`，它会把 `<AppID>:<openid>` 写入 `config/config/other.yaml` 的 `master` 列表，于是该 openid 在这个 bot 上的 `isMaster` 变为真。登录成功的回复里追加一行指引。

不提供「首个私聊者自动成为主人」的认领窗口。

## Testing Decisions

好测试的标准：只断言外部可观察的结果——给定的输入段/消息/配置，产出什么发送请求、什么配置差异、什么文本。不测私有方法，不测中间变量，不断言日志文案。

四个测试缝，全部是已有的纯函数或已有的边界：

1. **消息段拆分**（已有）——喂合并转发段，断言产出的文本块；顺带覆盖现有的文本/媒体/引用行为不回归。
2. **摘要识别与页脚剥离**（新增纯函数）——覆盖三种情况：带页脚、无页脚、无 `assistant-reply`；页脚形态覆盖粘行、缩进、叙述提及三种。
3. **通道策略解析**（新增纯函数）——输入窗口键与配置，断言返回的参数；非官方机器人窗口返回全局值。
4. **锅巴账号差异**（新增）——喂一份提交数据与一个内存版账号表，断言删了谁、改了谁、没碰 secret。

既有先例：适配器与消息段的测试都是「构造输入对象 → 断言发出的请求体」，测试里用假的 api 与内存版账号表，不启动网关、不联网。新增测试沿用同一套写法。

## Out of Scope

- **免前缀**。讨论后取消：`quickSend` 是 catch-all 规则，去掉前缀门槛后会把该 bot 会话里所有无前缀消息抢走，其它插件的闲聊型功能失效；而为了保证 `#hapi` 指令不被当成对话内容，还得再加一道「以 `/` 或 `#` 开头就不处理」的闸门。收益（少打一个字符）低于代价，继续用 `>`。
- **登录时自动设主人**。扫码接口虽然返回扫码人的 openid，但那是未公开接口里的可选字段，AstrBot 完全不读，不能作为权限依据。
- 锅巴里渲染二维码（组件白名单里没有图片组件）。
- 非主人的访问授权。
- 按账号独立的策略（策略是全局的）。
- 频道富媒体（目前只支持图片）。
- QQ 官方 markdown 对表格的支持（需实测，本期不做自动降级）。

## Further Notes

**扫码能拿到什么**：绑定轮询在 `status = 2` 时返回 `bot_appid` 与 `bot_encrypt_secret`，AppID 正是靠前者落库的，缺了会直接报「未返回完整凭证」。扫码人的 `user_openid` 是同一响应里的可选字段，AstrBot 只取 `bot_appid` + secret，我们也只是顺手读、没有任何地方消费它。结论：**Bot 的 id 确定能拿到，扫码人的稳定身份不能**。

**为什么必须修合并转发**：这不是优化。hapi 的文本推送全部经由「节点数组 → 合并转发段」这条路径，适配器拆出空数组后直接返回成功，用户侧表现是「完全没有反应」。在这个问题修好之前，通道策略调什么都没意义。

**主人为什么还是要设**：官方机器人的 `self_id` 是 AppID、`user_id` 是 openid，都不在 Yunzai 的 `masterQQ` 里，所以 `isMaster` 对它恒为假——不设主人，`#hapi` 指令和 `>` 快捷发送都用不了。这是继续用前缀方案的前提。
